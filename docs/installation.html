Installation

Two ways in: a minimal stack pasted without cloning anything, or the full stack with server control, saves and mods.

Which one?#

MinimalFull
Roles, quick actions, custom commands, audit logYesYes
Raw RCON console (administrator)YesYes
Players and UPS graphsYesYes
CPU and memory graphs—Yes
Server tab: start, stop, restart, logs—Yes
Saves tab: archives, schedule, download, restore—Yes
Mods tab: portal search, install, update, enable, remove—Yes
Containers2: Factorio, the panel4: + control agent, data agent
Docker socket mountedNowhereIn the control agent only
NeedsA docker-compose.yml and a .envA clone of the repository

Both keep the panel's data in the same named volume, so starting minimal and moving to the full stack later loses nothing.

Requirements#

  • Docker and the Compose plugin, on linux/amd64 or linux/arm64;
  • a headless Factorio 2.x server with RCON enabled — both compose files below provide one (factoriotools/factorio);
  • for the full stack: git, openssl, and access to the Docker socket for ./setup-admin.sh; a factorio.com account if you want to install mods from the portal;
  • nothing else: the panel ships its own SQLite storage (node:sqlite, built into Node, no native dependency to compile).

Minimal install, without cloning#

The panel's image is published, so the repository is optional: one directory, the docker-compose.yml below pasted as it stands, and a generated .env next to it. Both the game server and the panel come up with docker compose up.

services:
  factorio:
    container_name: factorio-server
    image: factoriotools/factorio:stable
    restart: unless-stopped
    ports:
      # Game port only. RCON stays unpublished: the panel reaches it over the
      # compose network, and the port hands full server control to whoever
      # holds the password.
      - "34197:34197/udp"
    volumes:
      - ./data:/factorio
    environment:
      # The image's own mod updater. It needs factorio.com credentials
      # (USERNAME and TOKEN): set them before turning it on.
      - UPDATE_MODS_ON_START=false

  factorio-admin:
    container_name: factorio-admin-panel
    # A minor tag: patches arrive, a major never lands on you by surprise.
    # In production, pin the exact version instead.
    image: williamnauroy/factorio-admin-rcon:1.5-distroless
    restart: unless-stopped
    depends_on:
      - factorio
    ports:
      # Loopback only: the panel grants full RCON access.
      - "127.0.0.1:3010:3000"
      - "[::1]:3010:3000"
    volumes:
      # The directory, not the file: a regenerated rconpw is picked up as is.
      - ./data/config:/factorio-config:ro
      # Sessions, audit log and metric series (SQLite).
      - factorio-admin-data:/data
    read_only: true
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=16m
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    mem_limit: 256m
    pids_limit: 128
    environment:
      - RCON_HOST=factorio
      - RCON_PORT=27015
      - RCON_PASSWORD_FILE=/factorio-config/rconpw
      - ADMIN_PASSWORD=${ADMIN_PASSWORD:?set it in .env}
      - SESSION_SECRET=${SESSION_SECRET:?set it in .env, 32 chars minimum}
      # No agents in this stack: no Server, Saves or Mods tab, no CPU and
      # memory graphs. Players and UPS keep working.
      - CONTROL_ENABLED=false
      - METRICS_DOCKER=false
      - SAVES_ENABLED=false
      - MODS_ENABLED=false

volumes:
  factorio-admin-data:

The secrets are generated rather than typed. For this minimal stack, the two relevant values are:

cat > .env <<EOF
ADMIN_PASSWORD=$(openssl rand -base64 18)
SESSION_SECRET=$(openssl rand -hex 32)
EOF

docker compose up -d
cat .env            # the password to log in with
                    # → http://127.0.0.1:3010

MODERATOR_PASSWORD and VIEWER_PASSWORD are optional: add them to .env and to the service's environment: to open the two read-only roles. A role without a password has no account at all.

The first start reports RCON as unavailable The game server is still creating its map, and data/config/rconpw does not exist yet. The panel re-reads that file on every connection attempt, so it recovers on its own after a few seconds — no restart needed.

Updating is a pull, since nothing is built locally: bump the tag, then docker compose pull && docker compose up -d.

Full install, every feature#

The repository's docker-compose.yml runs the four services, their networks and their secrets, already confined. ./setup-admin.sh prepares everything they need on the host.

git clone https://github.com/EdwinAlkins/factorio-admin-rcon.git
cd factorio-admin-rcon

./setup-admin.sh
docker compose up -d --build control-agent data-agent factorio-admin
# → http://127.0.0.1:3010

Compose starts the factorio service along with them. What ./setup-admin.sh does, all of it safe to run again:

  • writes .env: the administrator password and SESSION_SECRET, kept if already there;
  • generates the two agent tokens, secrets/control-agent-token and secrets/data-agent-token;
  • creates an empty secrets/factorio-portal ({}), which it never overwrites;
  • creates backups/ and hands it to uid 845, the data agent's;
  • records DOCKER_GID, the group owning the Docker socket on this host, for the control agent.
./setup-admin.sh --all          # moderator and viewer passwords too
./setup-admin.sh --ask          # prompt for the passwords instead of generating them
./setup-admin.sh --force --yes  # full rotation, no questions asked (ends every session)

To install mods from the portal, add your factorio.com credentials to secrets/factorio-portal and recreate the data agent — see Portal credentials. Without them, the Mods tab still lists, enables, disables and removes mods.

SESSION_SECRET is required Without it, Compose refuses to start the service. That is deliberate: the cookie signing key must not be derived from the passwords, otherwise changing one password signs everybody out. setup-admin.sh generates it.

What gets mounted#

MountIntoPurpose
./datafactorioThe game's folder: saves, mods, config.
./data/config:/factorio-config:ropanelThe RCON password (rconpw, regenerated by the game server) and, if you have one, your command catalogue. The directory is mounted rather than the file, so a recreated file is picked up without a restart.
factorio-admin-data:/datapanelNamed volume: sessions, audit log, metric series, backup schedule and operation history (SQLite). It is the only place the panel writes to.
/var/run/docker.sockcontrol agentThe panel calls the agent's closed, token-protected API and never receives the socket. DOCKER_SOCKET overrides the path (rootless Docker).
./data/saves, ./data/modsdata agentRead-write: restores write saves, the Mods tab installs and removes mods.
./backupsdata agentArchives, outside ./data so they can be replicated on their own. Must belong to uid 845.
secrets/*-agent-tokenpanel, one agent eachCompose secrets, one per agent.
secrets/factorio-portaldata agentfactorio.com credentials, or {}.

The panel and both agents run with a read-only root filesystem, cap_drop: [ALL], no-new-privileges, and memory and PID caps (256 MB for the panel, 32 MB and 128 MB for the agents). None of them runs as root: the panel as uid 1000, the control agent as 65532 plus the socket's group, the data agent as 845. The Services page explains who holds what, and how to remove an agent you do not need.

Published images instead of a local build#

The compose file builds the three images from the clone. Releases also publish them, for amd64 and arm64, with an SBOM and build provenance: swap each build: block for an image: line. Keep the three on the same version — the panel and its agents speak a private API, versioned together.

  control-agent:
    image: williamnauroy/factorio-control-agent:<version>
  data-agent:
    image: williamnauroy/factorio-data-agent:<version>
  factorio-admin:
    image: williamnauroy/factorio-admin-rcon:<version>-distroless

Hardened image (optional)#

Dockerfile.distroless produces a variant of the panel with no shell and no package manager, published under -distroless tags. It is the variant the docker-compose.yml uses by default. It shrinks the attack surface at the cost of less convenient debugging: no docker exec … sh. Both agents are distroless already: a static Go binary and nothing else.

Upgrading from 1.x#

2.0 replaces the docker-proxy service (tecnativa/docker-socket-proxy) with the project's own control agent, and adds the data agent. With CONTAINERS=1, that proxy answered for every container on the host, environment variables included — so the panel's own ADMIN_PASSWORD and SESSION_SECRET were one request away from anything that reached it.

  1. take the new docker-compose.yml (or port its control-agent and data-agent services, its networks: and secrets: blocks into yours) and delete the docker-proxy service;
  2. run ./setup-admin.sh once: existing passwords are kept; it adds the agents' tokens, an empty secrets/factorio-portal, backups/ and DOCKER_GID;
  3. drop DOCKER_API_URL, METRICS_CONTAINER and DOCKER_TIMEOUT_MS from your environment: the panel no longer reads them;
  4. set UPDATE_MODS_ON_START=false on the factorio service, as the new compose file does: otherwise the image replaces the versions chosen in the Mods tab with the newest at every start. Keep it true, with MODS_ENABLED=false, if you manage mods outside the panel;
  5. docker compose up -d --build --remove-orphans.

Behind a reverse proxy#

The panel only listens on the loopback interface. To expose it, put a TLS reverse proxy in front and enable TRUST_PROXY:

TRUST_PROXY=true
Only enable TRUST_PROXY behind a proxy you control It makes the panel trust X-Forwarded-For for per-IP rate limiting. Exposed directly, anyone forges that header and resets their own counter on every attempt. While it is false the header is ignored and rate limiting falls back to a global bucket — coarser, but unforgeable.

The session cookie turns secure on its own as soon as the request arrives over HTTPS (COOKIE_SECURE=auto, the default). Recipes for Caddy, Nginx, Traefik and Tailscale are in Deployment.

Health probes#

RouteAnswersUse it for
/api/health200 as long as the process is aliveDocker's liveness probe. It does not depend on Factorio.
/api/ready200 when configuration, command catalogue, database and RCON answer, plus the control agent when server control or Docker metrics use it, and the data agent when saves or mods do; 503 otherwiseThe readiness probe. Kept separate from the above so a Factorio outage does not restart the panel in a loop.

Each agent image carries its own Docker healthcheck (the binary run with -healthcheck), so docker compose ps shows them healthy or not.

Updating#

# Minimal stack: bump the tag in docker-compose.yml, then
docker compose pull && docker compose up -d

# Full stack, built from the clone
git pull
docker compose up -d --build control-agent data-agent factorio-admin

Published images follow the versions semantic-release cuts. The database schema is upgraded at startup: columns added after the fact are caught up by an idempotent ALTER TABLE, so there is nothing to do by hand.
