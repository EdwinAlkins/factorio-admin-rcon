Services

Four containers, three networks, and who holds what. Then the three tabs they make possible: Server, Saves and Mods.

The panel talks RCON to the game server and nothing more. Everything that needs more reach goes through one of two small Go agents (services/agents), each holding exactly one dangerous thing: the control agent holds the Docker socket, the data agent holds the game's files and the only way out to the Internet. Neither can do the other's job, and the panel can do neither on its own. A compromised panel can ask to stop the server or restore an archive that already exists; it cannot name another container, run a command in one, or write a file of its choosing.

Turning features off#

Every feature that needs an agent has a switch. Once nothing uses an agent, delete its service from the compose file: a privileged container kept running for a disabled feature is all cost and no benefit.

Some features lean on both agents Applying mods stops and restarts the server, so it is refused with CONTROL_ENABLED=false. Saves work without the control agent, with two caveats: a backup archives the newest save file as it is, without asking Factorio to save first, and a restore cannot stop the server — stop it yourself before restoring.

The control agent#

The only container that mounts the Docker socket. It does not expose the Docker API: it answers a closed list of operations — status, CPU and memory, logs, start, stop, restart — on the one container carrying this stack's factorio Compose service label. No route takes a container id. There is no code for exec, for creating or deleting a container, or for images, volumes and networks. Its answers are built field by field, so no container's environment, the panel's own secrets included, ever leaves it.

It still is the most privileged component of the stack, so it runs as a non-root uid with only the socket's group added (DOCKER_GID), read-only, with every capability dropped, 32 MB and 32 PIDs. API and threat model: services/agents/README.md.

The data agent#

The only container that writes the game's files. It archives saves, verifies them, streams them for download and restores them; it installs, updates, enables, disables and removes mods. It never sees the Docker socket: stopping the server around a restore or a mod change is the panel's job, through the control agent.

  • It runs as uid 845, the factoriotools/factorio image's, so the files it writes keep the owner the game expects.
  • It only reads and writes three folders — saves, mods and backups — and one file of a fourth, config/server-settings.json. A restore or an install verifies every archive entry by entry before writing anything.
  • It is also the only component that reaches the Internet, and only mods.factorio.com and its download host dl-mod.factorio.com, over HTTPS. No request carries a URL: they are built from a fixed base and validated mod names, and every redirect is checked against those two hosts.

Server tab#

The container's state as Docker sees it, and the game's as RCON sees it. That pair is what tells a server stopped on purpose from one whose RCON is down.

RoleSeesCan
viewer, moderatorState, players, version, uptime, recent operations—
adminThe same, plus the last 200 log linesStart, stop, restart; edit the server settings

A stop, or a restart, runs in order:

  1. refuse if players are online or RCON does not answer, unless the administrator confirms a second time;
  2. /server-save over RCON, then wait until the log reports the save written (CONTROL_SAVE_TIMEOUT_MS, 2 minutes by default). On timeout the server is left running;
  3. ask Docker to stop the container, with STOP_TIMEOUT_SECONDS (60 s) of grace before SIGKILL.

A start returns once RCON answers.

Server settings#

The tab edits server-settings.json: the name, description and tags of the listing, its visibility, the player limit, autosaves, pause and network settings, and the passwords. Factorio reads the file when it starts, so a change is either saved for the next start — the server keeps running, Factorio never writes the file back — or saved and applied: written, then the map saved and the server restarted, with the same players-online check as a restart. If the server does not come back, the previous file is put back and the server started again.

  • Only the keys the tab shows are rewritten. Comments, keys of a newer Factorio and anything added by hand are kept, in their order; blank lines between groups are not.
  • The game password and the factorio.com token and password are never sent to the browser: the tab only says whether each is set, and can replace or clear it. The audit log names the keys changed, never a value of theirs.
  • A public game needs a factorio.com username and a token or password: a change that would publish without them is refused.
  • The five previous versions are kept in ./backups/.server-settings/.

This needs ./data/config mounted in the data agent, as the compose file does. A stack set up before this feature does not: the tab then says so, and the rest works as before. The folder also holds rconpw; the agent opens nothing else there, and could not use it anyway — it is not on the game network.

One operation at a time#

Start, stop, restart, a backup, a restore, an import, a mod change and applying server settings share a single lock: a second request gets 409 operation_in_progress instead of racing the first. Each operation runs in the background (the route answers 202), reports its steps as it goes, and lands in the audit log and in the history shown on the Server tab. One cut short by the panel restarting is marked interrupted.

Saves tab#

The server's saves folder and the panel's archives, side by side. Moderators see both. Archiving, downloading, restoring, deleting and the schedule are for administrators. Viewers do not see the tab.

  • Back up now asks Factorio to save, waits for the save to be written, then archives it.
  • Download streams the archive. It is a full copy of the world, so it is audited.
  • Delete removes an archive and its sidecar.

Import a save#

Sends a .zip save from your computer — a single-player map, or one from another server — up to SAVES_MAX_UPLOAD_MB (2048 by default). It goes in 8 MB pieces, so a dropped connection resumes where it stopped rather than from zero, and no single request outlives a proxy's timeout. The data agent then reads it back in full, as it does any archive, and keeps it as an archive of source imported. Nothing reaches the saves folder at that point: playing it is an ordinary restore, with its safety archive and its rollback.

A save does not state its game version or mod set in a stable form, so an imported archive records neither, and the restore cannot compare them: the dialog says so. A map's scenario scripts run on the server, which is why importing is for administrators only, and audited.

Behind nginx, raise client_max_body_size to 10m: its default, 1 MB, refuses every piece.

Scheduled backups#

Set in the tab, stored in the panel's database, and run by the panel's own process: there is no cron to install.

By default a scheduled run archives the newest autosave rather than triggering a save, which would freeze the game while it is written. Retention only ever prunes scheduled archives: manual ones stay until you delete them. Safety archives, those taken before a restore or a mod change, have their own policy, applied after each scheduled run: the last 10, for 30 days at most, and never one less than a week old.

Restore#

One operation, from start to finish:

  1. verify the archive against its recorded checksum. A damaged one is refused here, before the server is touched;
  2. refuse if the game version or the mod set differs from the archive's, or if players are online, unless the administrator confirms a second time;
  3. save, then stop the server;
  4. take a safety archive of the current state (pre-restore);
  5. restore, start the server, wait for RCON.

If the server does not come back, the safety archive is restored the same way and the server started as it was. The operation ends in error either way, and says whether that rollback worked. Nothing is destroyed along the way: the saves a restore replaces are moved to replaced-<time>/ in the backups folder, out of Factorio's sight (the three latest sets are kept).

The restored file is written last, with the current time, so factoriotools/factorio's default (LOAD_LATEST_SAVE=true) loads it. For a server started on a fixed SAVE_NAME, set TARGET_SAVE_NAME to that file name.

What an archive is#

A zip of the save in ./backups, plus a JSON sidecar recording its source (manual, scheduled, pre-restore, pre-mods), who asked, its size and SHA-256, the Factorio version and the mod set at the time. An archive describes itself: the panel's database is not needed to know what it is. Every copy is written atomically and verified entry by entry. Archives are plain files: copy them off the host with whatever you already use (rsync, restic, a NAS share). See Deployment.

Mods tab#

Every role sees the server's mods: version, enabled or not, update available. Changing them is for administrators, and goes through a basket:

  1. add changes: install from the portal, update, enable, disable, remove, up to 50 at once;
  2. preview what they amount to. Nothing is written;
  3. apply them all as one operation, with a single restart.

The preview#

Dependencies are resolved the way each mod's info.json declares them: required, ? optional, ! incompatible, ~ does not affect load order, and version constraints. For each mod, the preview picks the newest release for this game's version that satisfies every enabled mod, then pulls its required dependencies in, recursively.

What cannot be satisfied is a conflict, named rather than guessed around: disabling a mod another one needs, an incompatibility, no release for this Factorio. The panel never silently downgrades something else to make room. The preview carries a hash; if a release is published between preview and apply, the apply is refused (plan_changed) and you preview again.

Applying#

  1. download and verify every archive, with the server still running: the portal's SHA-1, every entry's CRC, names that stay inside the archive, a single top folder, an info.json naming the expected release. A slow portal or a bad download disconnects nobody;
  2. refuse if players are online or RCON is down, unless confirmed a second time;
  3. save the map, stop the server;
  4. archive the map (pre-mods, labelled before mods: …, in the Saves tab);
  5. swap the mods in and rewrite mod-list.json, keeping every entry it does not change;
  6. start the server and wait for RCON.

If the server does not come back, the previous mods are put back from a journal and the server restarted as it was, within seconds. A server that was stopped stays stopped: the new mods load at its next start.

What the tab does not touch#

  • Built-in mods (base, recycler…) can be disabled, never removed.
  • elevated-rails, quality and space-age follow the image's DLC_SPACE_AGE variable, which it reapplies at every start. Change it on the factorio service.
  • Mods installed as folders are listed and can be toggled, never replaced or removed.
  • Mod settings (mod-settings.dat) are not edited.

Portal credentials#

Searching the portal and downloading need a factorio.com account, the same one the game uses. Without it, the tab still lists, enables, disables and removes mods, and shows the updates available.

# Token: https://factorio.com/profile, or player-data.json in the game's folder
cat > secrets/factorio-portal <<'EOF'
{"username": "your-name", "token": "..."}
EOF

# Recreate, do not restart: an editor saving the file replaces it, and a
# running container keeps seeing the old one.
docker compose up -d --force-recreate data-agent
Set UPDATE_MODS_ON_START=false on the game server With it on, factoriotools/factorio replaces every mod with its newest release at each start, undoing the versions the tab chose. The repository's docker-compose.yml sets it off. Keep it on, with MODS_ENABLED=false, only if you manage mods outside the panel.

The tab needs to know the game's version to pick releases. It reads it over RCON, and remembers the last one seen: start the server once before installing your first mod.
